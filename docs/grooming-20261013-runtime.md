## Demonstrated salvage defects and shared correction

`ConstructionMaterialResolver` previously selected the first crafting recipe producing an item, preferred one ingredient alternative, and ignored every other construction route. A target craftable from cobblestone could therefore recycle the diamonds in a different recipe. Recipe iteration order selected the payout. Returned containers/catalysts could also be credited as consumed ingredients.

The resolver now intersects the amounts of unambiguously consumed materials across observed native shaped/shapeless construction recipes, normalized by output count. A container is not a fully consumed material. A custom recipe that advertises the same output but lacks a proven consumption bill prevents an invented material payout. One-for-one upgrades consuming their own target do not erase original construction evidence; a recipe producing more targets than it consumes must participate in the proof. Material output never includes the recycled target itself.

The old hardcoded Ascendance-equipment decomposition was also removed. It claimed a one-ingot construction backed by independent Essence spending. Actual Latent equipment uses ordinary loaded shaped recipes (for example, three Latent Ingots and two sticks for the pickaxe), and initial crafting spends no Essence. First-party equipment now uses the same evidence boundary as other items and cannot bypass a cheaper datapack recipe.

`GatheringSalvageService` previously rounded each material independently, applied a sequential cap, then paid a weighted fallback if all rolls failed. That fallback biases the material mixture. For a bill of 0.25 diamond plus one stick and recovery 90%, the one-item cap produced approximately 0.2405 diamond per salvage; the proportional one-item reward should average 0.2 diamond. The runtime now samples a bounded total first and allocates it proportionally. For total construction units `U > 1`, expected recovered units are `min(ceil(U)-1, max(1, U*f))`; each material's expectation is its proven amount multiplied by total recovery divided by `U`. The upper bound is strictly below `U`, preserving material loss even when configured recovery is very high.

The meaningful one-item recovery remains whenever a proven bill supports it. If routes have no shared material, only one common material unit, opaque consumption, or too many outputs for the consumed bill, both a guaranteed recovered item and material loss cannot be established. The custom recycle action now rejects these items intact even when they contain enchantment XP, enforcing its authored material guarantee; ordinary native grindstone disenchanting remains available. Proven material recycling still also grants legitimate enchantment-derived bonus XP. This is an explicit item-evidence incompatibility, not removal of Salvager's Craft or weakening its authored rank floor. Unknown dynamic recipes whose output itself cannot be observed remain an evidence limitation. Small valid bills can saturate at one recovered item; skill rank improvements must therefore be evaluated on supported unsaturated bills as conditional mechanics, not assumed for every recycled item.

No saved investment unit, rank receipt, profile, human configuration, or existing equipment data format changed. The runtime salvage correction takes effect without a balance rebuild. New generated skill/Bonus profile changes in the wider checkpoint have their own rebuild requirements.

The current salvage proof is **expected per-material conservation**, not a worst-case guarantee for each individual random payout. Material selection with replacement can return several units of one ingredient, and a fractional bill can return one ingredient unit despite requiring less than one per crafted output. The roll happens only after consuming the input; the HUD exposes readiness and the previous result, not a rerollable payout preview. The existing localized contract explicitly guarantees at least one material. A two-unit proven bill plus strict material loss therefore forces exactly one payout at every rank; this is a genuine saturation incompatibility, not proof of meaningful later ranks. The live census below measures this boundary; no unconditional all-item minimum is claimed here.

Native recipe class identity alone does not establish its ingredient bill. Both loader APIs explicitly permit complex custom ingredients to expose incomplete display stacks. The resolver now accepts custom item alternatives only under the loader's explicit simple/no-testing completeness contract, and excludes unreadable or arbitrary subclass predicates from both paid-material recovery and the self-upgrade shortcut. Focused tests use each installed loader's actual custom wrapper: a predicate displaying diamond while accepting cobblestone cannot return diamonds, ordinary guaranteed sticks remain recoverable, and explicitly complete simple custom ingredients stay supported.

Stack-sensitive remainder overrides are likewise unproved consumption. NeoForge's stack remainder hooks and Fabric's `getRecipeRemainder(ItemStack)` can return the paid item for selected component states; a default-stack sample would not prove all accepted inputs are consumed. The resolver detects overrides against the loader's base Item contract and excludes those materials while retaining ordinary item behavior. An adversarial item that returns its input through both loader hooks verifies this boundary without registering fixture content into the live registry.

## Carrier denomination compatibility

`EssentiumCarrierData.readValidated` previously compared the saved exact amount with the **current** grade capacity. A legitimate old carrier became unusable for Crucible dissolution or block placement when a rebuild lowered capacity. A capacity increase preserved dissolution but all four compression recipes still required equality with the new capacity, stranding the old denomination. The raw NBT survived, but its value was functionally inaccessible.

New mints store carrier schema 1 and `ingot_denomination`, alongside unchanged Essence, grade and exact amount. Server reads validate the saved form capacity against that denomination, independently of the active mint profile. A fixed bound (`Long.MAX_VALUE / 1,000,000`) preserves representability in the existing micro-unit ledger; a denomination must be divisible by nine and permit every form within that bound. These bounds exceed all legitimate capacities admitted by the existing runtime-profile validator and do not reprice saved units.

Legacy carriers retain their exact stored face value. They have no historical provenance or mint-capacity field, so a positive, correctly typed amount within the accounting bound remains accepted. Compression infers a denomination from that amount and carrier form only when the complete 9:1 family is exactly representable. Nine matching inputs become their exact summed face value; splitting divides that amount exactly. Mixed Essence, grade, or face denominations are rejected. A declared partial schema-1 carrier remains dissolvable but cannot mint full outputs. An ambiguous legacy partial amount can transform into an inferred smaller denomination only with exact conservation. No inventory is migrated or rewritten on read.

The old current-capacity restriction did not authenticate a mint: arbitrary custom-NBT editors could already fabricate any amount below today's cap. No ordinary survival route was found that can edit the stored amount; minting pays for the target capacity, and all conversions preserve face value. The new metadata is likewise structural validation, not cryptographic provenance. Malformed/negative/overflow amounts, unknown schema, wrong numeric types, impossible denominations, and overfilled declared forms are rejected. Extraction still uses the current explicit extraction-efficiency policy; a profile can change that policy, but it does not change stored face value or denomination.

`NativeCarrierCompatibilityTest` covers all six Essence types and five grades under lower and higher replacement capacities, both legacy and schema-1 carriers, all four actual custom recipes, mixed values, partial values, malformed data, native ItemStack and placed-block NBT roundtrips, and real Crucible consumption of an older higher-capacity nugget. It runs inside `NativeResourceChainsTest` on both loader fixtures; exact execution status belongs to the root receipts. This runtime compatibility correction requires no balance rebuild.

The root independently isolated this carrier change, passed both loader native runs with 3,135 carrier checks each, and integrated verified checkpoint `08cee66`. Subsequent experimental balance work remains separate. The economics reviewer also independently confirmed the recipe helper's final exact input/output-value equality and fixed accounting bound; no arithmetic overpayment path was found.

Each item/rank records the effective expected recovery fraction, increment, saturation, masking, guaranteed first material, and strict expected loss. Confirmed native under-floor rows remain `FAIL` even when acquisition evidence is unknown. ## Purchase, persistence, activation, and composition review

`AscendanceNexusTransactionService` validates complete Bonus state, rank changes, prerequisites, selections, milestones, and optional Ascension before one atomic commit. `BonusTransactionPlan` uses exact long arithmetic for cross-funding Bonus and skill refunds/spending. `SkillPurchase` retains a cost for every paid rank; refunds use these receipts rather than current prices. Current tier caps preserve stored over-cap investment while blocking new increases. No new defect was demonstrated in these paths during this review.

`CommittedSkillService` shares authoritative evaluation across gameplay and diagnostics, keyed by player data identity, Nexus revision, configuration identity, and invalidation generation. `SkillEffectRuntime` applies the same generated native rank parameters used by previews, invalidates in-flight attack authority after rank/loadout changes, and deactivates removed handlers. Secondary damage uses scoped recursion/attribution protection; reflected and proc damage does not become a primary hit that retriggers offensive chains or life steal. Native health/absorption writes distinguish confirmed loss from restoration and nested damage. These are reviewed contracts; existing native regression suites provide scenario-specific execution evidence.

Composition boundaries already represented in native resource-chain fixtures include harvest to fuel-consuming cooking to food/health/repair, fishing to food, overlapping processor auras, bounded restocking, potion relay, sanctuary, and explosion containment. Salvage now adds recipe-route and rounding conservation. A repairable tool is required for meaningful maintenance; ordinary inactivity/food supplies still constrain mending. Small or capped equipment contexts cannot be counted as unconditional rank improvements.
