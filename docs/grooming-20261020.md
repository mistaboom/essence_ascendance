# Runtime stability grooming October 20 2026

This pass reviews runtime stability and server authority at beta.11 (`acd2a22`), with extra scrutiny on the glaive and two-handed equipment added since the October 17 pass. It fixes two reproduced combat-input defects and repairs two outdated test fixtures. The baseline checks, final focused checks, six initialized-loader runs and both ordinary production builds pass.

## Reproduced defects and fixes

### Movement backlogs could accumulate unbounded glaive collision work

`WeaponActionRuntime.observeAim` retained every ordinary-range movement observation until the next authority tick. The next stab or swipe update traversed the resulting path. The long-range path already compressed observations, but ordinary ranges had no corresponding bound.

Each active action now accepts at most 16 native movement observations between authority ticks. A seventeenth cancels the action before more aim or collision work is accumulated. The server preserves the spent cooldown, applies no delayed damage or wear from the discarded backlog, and accepts a fresh attack after recovery. The counter resets each authority tick; ordinary within-tick turns retain their existing path.

The native regression sends 64 alternating rotations before advancing a tick, across all six equipment tiers and both attack modes. It checks cancellation, preserved recovery, absence of delayed damage/wear and subsequent attack acceptance. A separate multi-tick case verifies that ordinary movement receives a fresh budget each tick.

This bounds input-amplified action work; it is not a general network-flood or worst-case server-latency guarantee.

### Removed player input could poison the shared sequence

`WeaponActionRuntime.input` advanced its UUID-owned sequence before checking whether the actor could act. Although action acceptance already rejected a removed player, that old entity could still advance the sequence and cause the live player's later input to be rejected.

The input boundary now rejects dead, removed and spectator actors before accessing the gate or advancing its sequence. The native regression submits a maximum sequence from a removed entity, then verifies that ordinary live input with sequence 1 still succeeds and has no inherited cooldown.

### Machine fixture initialization skipped native listeners

The shared simulated-player setup now creates an inventory menu. `NativeMachineBindingTest.initializeMenuLifecycle` treated that menu as proof that all native menu lifecycle fields existed, leaving its listener and synchronizer null. The actual `ServerPlayer.openMenu` path then failed during team disband/menu renewal.

The fixture now initializes each missing field independently. Native menu opening, synchronization and authorization remain exercised. This was a fixture defect, not a reproduced gameplay crash.

### Movement fixture omitted the new offhand boundary

The client movement fixture supplied synthetic hand reads but omitted both the native inventory and consistent equipment-slot reads. The newer shield policy queries the offhand slot, exposing that incomplete setup. It also requires the server's synchronized offhand decision.

The fixture now supplies consistent held-slot state, a real empty inventory for other slots and an explicit synchronized hand decision. A new negative assertion verifies that server-denied offhand use revokes both shield guarding and guarded sprint. Native sprint, jump and terrain collision methods remain inherited.

## Acceptance boundary

These are source, invariant and initialized-loader checks using isolated fixtures that exit before opening a world. Real two-client sessions, live FTB roster changes, world/chunk unload and save/restart playtests remain separate acceptance work. Fixture logs contain deliberate failed-payment diagnostics and unavailable advancement-manager diagnostics from simulated servers.

The existing player/inventory/chunk saves are not one cross-file atomic transaction. Passing runtime rollback and serialization tests does not establish recovery from a forced process kill between those saves.

The fixes change transient input handling only. They require neither a new world nor balance regeneration. Existing Prism installations and worlds were not used as fixtures.
